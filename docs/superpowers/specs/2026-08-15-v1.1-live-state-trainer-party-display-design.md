| Status | Approved product direction |

## Outcome

DualScreenDex 1.1 expands the existing read-only Gen III runtime mapper into one typed live-game-state contract. The mapper covers the player, current location, complete party records, bag contents, battle records, and passive battle-menu state. Trainer Card and Party become first-class companion screens. Android display targeting gains event-driven recovery without changing the passive companion contract or sending game input.

The initial complete real control is official English Pokémon Emerald. The contract is deliberately data-driven so later source-backed Gen III engines can publish different addresses, field offsets, record widths, and pocket capacities without changing the runtime or web APIs.

## Existing baseline

The implementation already provides several foundations that must be extended rather than duplicated:

- `Gen3RuntimeMemoryLayoutResolver` derives the Gen III `Main` battle flag, live party count/array, `gBattleMons`, battle-type flags, and related cursors from compiled ROM references.
- `BattleMemoryCoordinator` owns the single read-only RetroArch memory session and already publishes live area, party, and battle updates.
- `Gen3PokemonCodec` validates and decrypts the 80-byte boxed Pokémon payload, while live party records are 100 bytes.
- `Gen3BattleLayoutResolver` decodes every active battler's four move IDs and PP values. `BattleObservationTracker` reveals opponent moves only after an execution signal or PP decrease.
- `DisplayTargetController` already supports `AUTO`, `HANDHELD`, and `EXTERNAL`, and `MainActivity` reapplies the preference on resume.

Version 1.1 must preserve those behaviors and their fail-closed boundaries.

## Source-mapping parity

The fork is used as a semantic inventory, not as an address map. Version 1.1 covers the same read-only data families through DualScreenDex's own typed mapper:

| Source-family state | DualScreenDex 1.1 authority | User-facing consumer |
| --- | --- | --- |
| `gSaveBlock2Ptr` player identity, Trainer ID, playtime, Pokédex, encryption key | validated SaveBlock2 pointer plus typed SaveBlock2 ABI | Trainer Card and bag decryption |
| `gSaveBlock1Ptr` location, money, party, bag, flags | validated SaveBlock1 pointer plus independently optional typed ABIs | Trainer Card, location, saved fallback, internal bag state |
| `gPlayerPartyCount` and `gPlayerParty` | existing structurally resolved live-party globals plus complete 100-byte record codec | Party overview/details and Team knowledge |
| `gBattleMons`, battle flags, action/move cursors | existing battle descriptor extended with optional passive-menu fields | existing battle UI and future passive extensions |
| Trainer front pictures and badge graphics | ROM-derived normalized catalog assets | Trainer Card |

No source symbol address, ROM name, filename, or ROM hash becomes a production selector. Source fields define meanings; decoded compiled consumers establish the runtime roots used by a specific ROM.

## Product scope

### Live-state mapping

The normalized live snapshot contains independently optional sections:

1. **Trainer**
   - player name and gender;
   - public trainer ID;
   - money;
   - playtime hours and minutes;
   - badge count and earned-badge bitmask;
   - Pokédex seen and caught counts;
   - Trainer Card star count when its source flags are proven; and
   - the selected normalized player-avatar asset when available.
2. **Location**
   - map group and map number;
   - player map coordinates;
   - normalized base-area ID and ROM-derived display name; and
   - normalized world-map location key when the catalog provides a unique join.
3. **Party**
   - slot and stable identity;
   - species/form, nickname, egg state, gender, level, and personality-derived nature;
   - current HP, maximum HP, status, and six current stats;
   - held-item ID;
   - experience and normalized progress to the next level;
   - exact ability slot and resolved ability ID when the catalog provides the species ability domain;
   - four move IDs, current PP, and maximum PP; and
   - existing IV and capture-ball data.
4. **Bag**
   - the five Gen III pockets as ordered `(itemId, quantity)` entries;
   - quantity decryption using the validated SaveBlock2 encryption key; and
   - an independent availability result for each pocket.
5. **Battle and passive menu context**
   - the existing complete battler records and target state;
   - wild/trainer/unsupported-special classification;
   - action-menu versus move-menu state when structurally proven;
   - current action and move cursor values; and
   - active player battler in single and double battles.

Bag and battle-menu context are mapped in 1.1 for future consumers, but 1.1 adds no bag screen and no touch battle controls.

### Trainer Card

Trainer Card is a full companion screen, not a modal and not an extra toolbar row. A compact semantic Trainer shortcut joins the existing Pokédex header actions. The screen shows the normalized avatar, name, public ID, money, playtime, seen/caught counts, stars when available, and eight badge positions. Earned badges use ROM-derived art; unearned badges remain subdued silhouettes. Missing optional values render as an em dash without exposing memory addresses or capability labels.

The player's own identity is never restricted by Organic mode. Missing avatar or badge artwork affects only that artwork; it does not hide the rest of the card.

### Party and Pokémon details

Party is a full companion screen reached from a compact semantic Party shortcut in the existing Pokédex header. No additional navigation row consumes vertical space.

The overview preserves party order and shows six stable slots with species artwork, nickname, level, HP, status, and held-item state. Selecting an occupied slot opens a live detail view containing nature, ability, held item, experience progress, current stats, and move PP. Species, move, type, and ability labels come from the active parsed catalog. If a referenced record is absent, the value is withheld rather than replaced with a raw numeric ID.

The player's party is owned information and remains visible in every knowledge mode. The existing Team filter and ownership ledger continue to use the same live party authority; the new screen must not create a second party state.

### Opponent move privacy

The live mapper may decode all four opponent move slots because they are necessary for structural validation and PP-delta observation. Those raw slots remain inside the battle-memory layer. Public companion state continues to receive only `MoveObservation` records generated after a move is executed or consumes PP. Discovered mode does not bypass this boundary for live enemy loadouts.

### Display continuity and recovery

The current display-target setting remains authoritative:

- `AUTO` preserves the display on which the user launched DualScreenDex.
- `HANDHELD` selects the Android default display.
- `EXTERNAL` selects a unique eligible non-default presentation display.

Version 1.1 adds a lifecycle-owned `DisplayManager.DisplayListener`. A pure continuity policy evaluates display-added, display-changed, display-removed, activity-resume, and setting-change events. It may keep the current host, move once to a uniquely resolved target, or remain on the current/default display when external selection is ambiguous.

Recovery rules:

- never choose an arbitrary external display when multiple candidates are equally eligible;
- never create two companion activities for one recovery event;
- never loop between displays after a failed launch attempt;
- retain the bundled WebView route and server-backed state across recreation;
- when an external display disappears, allow Android to return the task safely and re-evaluate on the next lifecycle event rather than repeatedly foregrounding the app over RetroArch;
- when the unique requested external display returns, restore it on the next visible companion lifecycle event; and
- preserve the existing non-focusable overlay behavior.

No timeout is used for display recovery.

## Architecture

### Typed catalog contract

`CatalogGen3RuntimeMemoryLayout` gains optional, validated descriptors rather than retail-only constants:

- SaveBlock1 and SaveBlock2 pointer globals;
- save-block byte extents;
- `Gen3TrainerCardAbi` field and flag offsets;
- `Gen3BagAbi` pocket offsets/capacities and encryption-key offset;
- `Gen3PartyAbi` count/address/record-size descriptors;
- `Gen3BattleUiAbi` menu-state/cursor descriptors; and
- optional normalized trainer asset keys.

Addresses originate in decoded ROM references. ABI offsets originate in source-family structure evidence and compiled field consumers. A missing or ambiguous descriptor remains absent. ROM name, filename, SHA, and absolute symbol offsets are permitted only in exact tests and reports, never in production selection.

Changing persisted runtime metadata invalidates catalog parser schema 9 and writes schema 10.

Parser-core owns the serialized `CatalogGen3*Abi` forms because it cannot depend on save-core. Save-core owns the runtime-neutral `Gen3*Abi` forms used by byte decoders. The Android integration layer performs one explicit, tested catalog-to-runtime mapping; it must not reinterpret offsets or add defaults. The existing top-level `CatalogRuntimeMetadata.gen3SaveBlock1PointerAddress` migrates into the complete runtime layout in schema 10 so there is only one pointer authority.

### Shared save-block decoders

Pure `save-core` decoders consume validated SaveBlock1/SaveBlock2 byte arrays and the typed ABI. The same code serves both sources:

- checksum-valid `.srm` reconstruction in `Gen3SaveReader`; and
- live WRAM blocks read through validated pointer globals.

This prevents live and saved Trainer/Party interpretations from drifting. Live data has priority while the matching RetroArch session is connected. The latest checksum-valid save remains the fallback after disconnect or when a live section is unavailable.

The save ABI also declares the selected Gen III text encoding. Player names and nicknames are decoded in save-core through that declared codec; the runtime and UI never guess an encoding from the displayed text.

### Runtime read orchestration

`BattleMemoryCoordinator` remains the only owner of the RetroArch memory reader. It builds one bounded read plan from the available descriptors, reads pointer globals before dependent blocks, rejects pointers outside GBA work RAM, and then publishes one immutable `Gen3LiveGameSnapshot`.

Each section carries its own capability result. A corrupt bag pocket does not remove Trainer or Party. A partial party record does not replace the last complete party. A validated zero-member party truthfully clears the live party.

Snapshots are not written into ROM, WRAM, SaveRAM, save states, cheats, controller input, or RetroArch configuration.

### Companion state and API

`AppSnapshot` gains one optional normalized player profile and one normalized live party list. `ProductionCompanionRuntime` merges live-over-save authority before publishing state. The API contains presentation-ready labels and asset URLs; it does not expose memory addresses, encryption keys, unobserved opponent moves, or raw unsupported IDs.

`AppScreen` gains `TRAINER` and `PARTY`. Back navigation returns to the exact prior screen. Battle updates continue in the background without forcing either new screen back to Battle.

### Normalized Trainer assets

The parser materializes player-avatar and badge graphics only after their compiled roles and dimensions validate. The first real control uses official Emerald's 64x64 Brendan/May front pictures and eight 16x16 badges. Assets are normalized to PNG, stored with the catalog, and served by catalog-owned loopback endpoints. Missing or ambiguous artwork uses existing silhouettes without substituting stock Pokémon assets.

Trainer assets occupy their own required schema-10 catalog section. A catalog either reopens with the exact declared Trainer asset keys and bytes or is reparsed; runtime metadata never embeds large image payloads.

## Data authority and lifecycle

1. ROM parsing produces immutable runtime descriptors and normalized Trainer assets.
2. Catalog storage persists those descriptors and assets.
3. Save parsing publishes a fallback player profile and detailed party from checksum-valid blocks.
4. The runtime coordinator reads the same fields from validated live pointers.
5. `ProductionCompanionRuntime` chooses live values for the matching active ROM and otherwise retains save-backed values.
6. API state exposes Trainer and Party views.
7. The web UI renders them without interpreting memory layouts.
8. Disconnect, ROM switch, or ambiguous live evidence clears only live authority; saved and catalog data remain intact.

## Validation and failure behavior

- Pointer globals must resolve uniquely from compiled ROM evidence.
- Every dereferenced GBA address must fit entirely inside EWRAM or IWRAM.
- Player names and nicknames must decode through the selected Gen III text codec and terminate within their declared widths.
- Money and bag quantities are accepted only when the encryption key and both participating save blocks are available.
- Party records require valid Pokémon checksum/decryption, species membership, bounded level/HP/stats, catalog-valid moves, and PP not exceeding the move's legal boosted maximum.
- Ability selection requires a valid stored ability slot and a catalog-resolved species ability domain.
- Trainer and Party snapshots reject internally contradictory values but do not invalidate unrelated sections.
- Display recovery rejects ambiguous external targets and records no permanent display ID as universally stable.
- All user-facing unavailable states remain short gameplay copy. Technical reasons remain in Diagnostics.

## Performance and privacy

- Pointer globals are read before dependent blocks; unchanged pointer targets are cached only for the active ROM session and revalidated on change.
- One live sample reads each selected region once. Trainer, party, bag, and battle consumers share the immutable sample.
- No second polling thread or second RetroArch transport is introduced.
- Bag data remains internal in 1.1, limiting API and UI surface until the item catalog is complete.
- Raw player names and party nicknames stay on-device and are never added to compatibility reports.
- Existing opponent-move Organic protections remain mandatory.

## Verification contract

Automated and real-control verification must cover:

- exact official Emerald ROM-derived SaveBlock pointer, party, battle, avatar, and badge descriptors;
- checksum-valid official Emerald SaveRAM decoding for Trainer Card and complete Party details;
- equivalent live WRAM byte windows producing the same normalized Trainer/Party values;
- invalid pointers, corrupt Pokémon checksums, invalid move/PP pairs, ambiguous descriptors, and independently unavailable sections;
- catalog schema-10 round-trip and schema-9 invalidation;
- no opponent move appearing publicly before execution/PP evidence;
- Trainer and Party navigation without a new toolbar row;
- compact and 4:3 presentation layouts;
- display add/change/remove policies, ambiguous external displays, failed-launch loop prevention, and state restoration; and
- the focused parser, save, battle-memory, catalog-store, companion-core, app, web, and production web-build suites.

Real source/ROM/SaveRAM controls lead each parsing slice. Small constructed fixtures and byte mutations are used only as bounded negative controls after the real structure is frozen; they are not evidence of compatibility by themselves.

No emulator, physical device, game command, release, or publication is required to complete the implementation branch. A later signed 1.1 release gate owns physical-display verification.

## Staged delivery

1. **Contracts and shared codecs:** normalized models, detailed Pokémon decoding, Trainer/Bag decoders, and saved-state fallback.
2. **ROM-derived live layout:** SaveBlock2 and semantic field descriptors, trainer assets, schema-10 persistence, and official Emerald controls.
3. **One live snapshot:** bounded coordinator reads and live-over-save runtime authority, with Bag/Battle UI retained internally.
4. **Trainer and Party presentation:** API, navigation, responsive pages, silhouettes, and privacy regressions.
5. **Display continuity:** event policy, lifecycle integration, loop prevention, and recovery state preservation.
6. **1.1 integration gate:** focused affected suites, production web build, clean diff, compatibility documentation, and implementation commits.

Each stage is independently commit-ready and must leave unsupported engines operating exactly as before.
